## 2. 4a — 클래스별 바이어스 벡터 (재학습 없음)

> **참고 (2026-09-07 이후 읽는 사람에게):** 이 절의 수치는 방법론 검증에 쓴 **step3(hard, seed 0)** 체크포인트 기준이다. `deliverable/`의 실제 후보는 이후 **seed1**로 교체됐고 그 값은 **§5.1**에 있다. 방법(바이어스를 어떻게 튜닝하는지, 왜 필요한지)은 두 체크포인트에 동일하게 적용되므로 이 절은 그대로 유효하다.

### 2.1 문제

Step 3은 클래스당 6,800개로 균형을 맞춰 학습했다(스펙 §1.3). 그래서 모델은 **균등 prior**를 학습했는데, 실제 면접 스트림은 중립이 지배적이다. 균형 테스트셋은 이 비용을 감춘다.

테스트셋을 서비스 prior(neutral .60 / anxious .15 / embarrassed .15 / happy .10)로 재가중하면 — 클래스 c의 샘플마다 `prior[c]/empirical[c]`를 곱한다. recall은 클래스 내부 비율이라 변하지 않고, precision만 움직인다:

| | anxious recall | anxious precision |
|---|---|---|
| 균등 prior — 원본 7클래스 | 0.5187 | 0.7010 |
| 균등 prior — 파인튜닝 | 0.7235 | 0.5990 |
| **서비스 prior — 원본** | 0.5187 | **0.5410** |
| **서비스 prior — 파인튜닝** | 0.7235 | **0.3588** |

서비스 prior에서 파인튜닝 모델은 전체 프레임의 **30.2%를 anxious로 부르고, 그중 54.9%가 중립 프레임**이다. (원본은 14.4%를 부르고 그중 31.9%가 중립.)

### 2.2 방법

로그 확률에 클래스별 상수를 더한 뒤 argmax:

```
adjusted = logprob + bias        bias = [b_hap, b_emb, 0.0, b_neu]
```

`bias[anxious] = 0.0`으로 고정 — 모든 클래스에 같은 값을 더하면 softmax 후 아무것도 바뀌지 않으므로 자유도 하나는 잉여다. `b_hap`도 0으로 고정하고 anxious로 새는 두 클래스만 스윕했다. **val에서만 튜닝**, test에서 보고 — τ와 같은 규칙이다.

### 2.5 기록용 — 지시받았던 0.10 기준 지점 (채택되지 않음)

제약을 원래 지시받은 0.10으로 두면 val에서 `bias = [0.0, 0.3, 0.0, 1.8]`이 선택된다. test 결과:

| | anxious recall | anx precision (서비스) | neutral→anxious |
|---|---|---|---|
| 원본 7클래스 | 0.5187 | 0.5410 | 0.0765 |
| ft + bias(0.10 기준) | 0.6129 | 0.4935 | 0.1221 |
| **ft + bias(0.08 기준, 채택)** | **0.6069** | **0.5439** | **0.0897** |

0.10 기준은 서비스 precision에서 원본에 못 미치고(0.4935 < 0.5410), val에서 만족했던 상한(0.099)이 test에서 0.1221로 넘어간다 — 660개 val 중립 프레임에서 고른 값이 2,720개 test로 그대로 유지되지 않은 사례다. 0.08 기준은 recall을 0.006 내주는 대신 서비스 precision에서 원본을 근소하게 앞서고, neutral→anxious도 val/test 간 이동폭이 작다(0.074 → 0.090). 이 비교가 0.08을 최종 채택한 근거다.

### 2.6 백엔드 계약 — 반드시 지킬 순서

`deliverable/meta.json`의 `bias` 필드:

```
adjusted = model(x) + bias        # bias = [0.0, 0.0, 0.0, 2.3], 클래스 순서 동일
prob     = softmax(adjusted)
pred     = argmax(prob)
accept   = prob.max() >= tau
```

**바이어스는 argmax 이전에, 그리고 τ 비교 이전에 더해야 한다.** softmax 이후에 더하는 건 틀린다.

**τ도 다시 뽑아야 한다.** 기존 τ=0.94는 바이어스 없는 확률 분포에서 고른 값이라 같은 의미가 아니다. 이 바이어스(`[0,0,0,2.3]`) 적용 후 val에서 다시 고른 값은 **τ = 0.96** (val 커버리지 0.628, test 커버리지 0.548, 통과분 정확도 0.9617)이다. `meta.json`의 `tau_biased`에 있다. 이전 0.10-기준 지점의 τ=0.93보다 높다 — bias가 커질수록(0→2.3) 확률 분포가 더 뾰족해지기 때문이다.

### 2.7 이 숫자가 기대는 가정

**서비스 prior 0.60/0.15/0.15/0.10은 측정값이 아니라 가정이다.** 실제 면접 스트림의 감정 분포는 아무도 재지 않았다. 서비스 prior 열 전체가 이 가정을 상속한다. 바꿔야 할 것이 있다면 Set B 녹화에서 실제 분포를 세는 것이다. 다만 **바이어스가 필요하다는 결론 자체는 prior 값에 둔감하다** — 중립이 균등(25%)보다 많기만 하면 방향은 같다.

## 3. 4b — Set A′: 실제 서비스 경로로 재평가

### 3.1 기존 평가가 빠뜨린 것

Set A는 **원본 해상도에서 크롭한 뒤** degradation을 건다. 서빙은 반대다: FE가 프레임 전체를 줄여서 보내므로 **MediaPipe가 이미 열화된 프레임 위에서 돈다.** 검출기 자체가 열화되고, 박스가 부정확해지고, 크롭이 흔들린다. 이 중 어느 것도 Step 3 숫자에 반영돼 있지 않았다.

A′는 그 경로를 그대로 재현한다:

```
원본 → EXIF 적용 → 프레임 전체를 224×224로 → 그 위에서 MediaPipe → 크롭(여백 0%) → 48×48 흑백 /255
```

같은 test split(`split.npy == 2`), 같은 2,720장, 같은 28명. 대조군으로 **짧은 변을 224로 맞추고 종횡비를 보존한** 경로도 같이 측정했다 — 4:3 프레임을 정사각형으로 늘리면 얼굴이 찌그러지므로, 대조군 없이는 성능 하락이 해상도 손실 때문인지 왜곡 때문인지 구분할 수 없다.

### 3.2 검출 — 백엔드에 좋은 소식

| | 실패 | 비율 |
|---|---|---|
| 224×224 스트레치 | **0 / 2,720** | 0.00% |
| 224 짧은 변, 종횡비 보존 | **0 / 2,720** | 0.00% |

**224×224 프레임에서 MediaPipe 검출 실패는 없다.** 얼굴 없는 프레임은 오답이 아니라 5초 판정 창의 구멍이 되므로 서비스 리스크였는데, 이 데이터에서는 발생하지 않는다.

부수적으로 스펙 §3.1의 예측도 확인됐다:

| | 값 |
|---|---|
| 224 프레임 내 얼굴 폭 | p5 69px / **중앙값 84px** / p95 110px |
| 스펙 §3.1 예측 | 80–120px |
| 검출 신뢰도 중앙값 | 0.889 (원본 해상도는 0.94) |

§3.2의 degradation 범위 72–132px는 실측 얼굴 크기와 정확히 겹친다. 증강 설계가 맞았다.

### 3.3 크롭 흔들림 — 거의 없다, 종횡비를 지키면

IoU(A′ 박스를 원본 좌표로 역투영, Set A 박스):

| 경로 | p5 | 중앙값 | 평균 | IoU<0.5 비율 |
|---|---|---|---|---|
| 224×224 스트레치 | 0.564 | 0.754 | 0.704 | 0.7% |
| **종횡비 보존** | **0.925** | **0.968** | **0.964** | **0.0%** |

**종횡비를 지키면 224px 프레임에서 검출해도 박스가 사실상 그대로다(IoU 0.968).** 즉 "검출기가 열화돼 크롭이 흔들린다"는 우려는 이 데이터에서 실질적으로 기각된다. 스트레치 경로의 IoU 0.754는 검출기 열화가 아니라 종횡비 변환 자체의 결과다.

| **A′ 224×224 스트레치** | **0.4393** | **0.2737** | **0.3209** |
| **A′ 종횡비 보존** | **0.8141** | **0.7274** | **0.8187** |

**종횡비를 보존한 A′는 Set A와 사실상 동일하다** (0.8187 vs 0.8194, 차이 0.0007). anxious recall도 0.6099 vs 0.6129, neutral→anxious도 0.1206 vs 0.1221로 모두 소수점 셋째 자리 차이다.

**즉 FE→BE 경로 자체는 성능을 거의 깎지 않는다. 깎는 것은 정사각형 스트레치 하나다.**

스트레치 경로에서 무슨 일이 벌어지는지 보면 명확하다 (균등 prior):

| | 원본 7c | 파인튜닝 | ft+bias |
|---|---|---|---|
| neutral recall | 0.3029 | **0.0691** | 0.1544 |
| neutral→anxious | 0.5912 | 0.3500 | 0.2647 |
| accuracy | 0.5478 | 0.4419 | 0.4562 |

찌그러진 얼굴에서 파인튜닝 모델은 **중립 프레임의 93%를 놓친다.** 원본 7클래스 모델이 상대적으로 덜 무너지는 건(0.5478) 성능이 좋아서가 아니라 원래 anxious를 잘 안 부르던 모델이 여기서도 덜 부르기 때문이다 — A′ 스트레치에서 원본의 anxious recall이 0.756으로 튀는 것도 같은 이유(전체의 57%를 anxious로 부른다)이지 실력이 아니다.

### 3.5 그래서 FE/BE에 물어야 할 것

> **FE가 카메라 프레임을 224×224로 보낼 때 종횡비를 어떻게 처리하는가?**
> (a) 정사각형으로 늘림 → **정확도 0.82 → 0.32. 즉시 고쳐야 한다**
> (b) 짧은 변 맞춤 + 중앙 크롭 / 레터박스 → 문제 없음

노트북 웹캠은 보통 16:9라 4:3인 학습 데이터보다 왜곡이 **더** 심하다(1.78배 vs 1.33배). 위 측정은 4:3에서 나온 것이므로 (a)일 경우 실제 하락폭은 이보다 클 수 있다.

이건 모델을 어떤 걸 쓰든 동일하게 발생하며, **Step 4에서 나온 어떤 모델링 개선보다도 크다.**

## 4. 4c — 3인 어노테이터 소프트 라벨 (재학습 1회)

### 4.1 방법

Step 2는 3명의 의견을 다수결 하나로 접고 불일치를 버렸다. 그 불일치는 노이즈가 아니라 **혼동이 실제로 일어나는 경계에 정확히 몰려 있다.**

```
hard:  anxious                    -> [0, 0, 1, 0]
soft:  2 anxious + 1 embarrassed  -> [0, 0.33, 0.67, 0]
```

§1.2 제외 규칙은 그대로다 — 같은 행, 같은 순서, 같은 split. 타깃만 바뀐다. 손실은 `-(soft * logprob).sum(1)`에 §3.4 샘플 가중치를 곱한 것이고, 타깃이 one-hot이면 `nll_loss`와 정확히 같으므로 만장일치 행에서는 두 경로가 일치한다.

스펙이 다루지 않은 경우 하나: 채택된 샘플도 범위 밖 투표(2 anxious + 1 분노)를 가질 수 있다. 그 표는 버리고 나머지로 재정규화했다 — 27,200행 중 **4,397행(16.2%)** 이 여기 해당한다.

### 4.2 불일치는 스펙 §1.3이 말한 곳에 있다

다수결 클래스에 실린 평균 가중치:

| 클래스 | 평균 | 만장일치 비율 |
|---|---|---|
| happy | 0.9825 | 94.8% |
| neutral | 0.9458 | 83.8% |
| embarrassed | 0.9161 | 74.8% |
| **anxious** | **0.8956** | **68.7%** |

반대표가 어디로 가는지 (다수결이 anxious인 샘플):

| 다수결 | happy | embarrassed | anxious | neutral |
|---|---|---|---|---|
| anxious | 0.010 | **0.216** | 0.667 | 0.108 |
| embarrassed | 0.042 | 0.667 | **0.191** | 0.100 |
| neutral | 0.049 | 0.118 | **0.167** | 0.667 |

**embarrassed↔anxious가 가장 큰 불일치 축이고, neutral→anxious가 그다음이다.** Step 3에서 혼동 행렬이 실제로 새던 두 자리와 정확히 일치한다. 스펙 §1.3의 "anxious 폴더 순도 37.8%"가 평균으로 뭉개지는 대신 학습 신호로 들어간다.

### 4.3 결과 — 같은 시드, 같은 split, 같은 증강

| 지표 (TEST, 균등 prior) | step3 (hard) | soft | 변화 |
|---|---|---|---|
| anxious recall | 0.7235 | 0.6996 | −0.0239 |
| anxious precision | 0.5990 | 0.6265 | **+0.0275** |
| neutral recall | 0.6853 | 0.7103 | **+0.0250** |
| neutral precision | 0.8944 | 0.8928 | −0.0016 |
| happy precision | 0.9620 | 0.9649 | +0.0029 |
| embarrassed precision | 0.7861 | 0.7727 | −0.0134 |
| accuracy | 0.7956 | 0.8048 | **+0.0092** |
| macro F1 | 0.7976 | 0.8055 | **+0.0079** |
| **neutral→anxious** | 0.2765 | **0.2441** | **−0.0324** |

**보정(calibration) — 여기가 진짜 개선이다:**

| | step3 (hard) | **soft** | 원본 7c |
|---|---|---|---|
| **ECE** | 0.0768 | **0.0269** | 0.1057 |
| MCE | 0.6569 | **0.3466** | 0.2575 |
| 평균 신뢰도 | 0.8698 | 0.8274 | 0.8874 |

**ECE가 2.9배 개선됐다.** τ는 이 신뢰도에 걸린 임계값이므로 이건 부수 효과가 아니다 — 보정이 나쁘면 val에서 고른 τ가 test에서 다른 의미가 된다. Step 3 §5에서 τ 선택이 "0.85~0.99 구간이 거의 평평해서 사실상 가장 보수적인 끝을 고른다"고 했던 문제의 원인이 여기 있었다.

그 증거로, soft 모델은 **바이어스도 덜 필요하다**: 같은 규칙(neutral→anxious ≤ 0.10)으로 튜닝한 결과가 hard는 `[0, 0.3, 0, 1.8]`, soft는 `[0, 0, 0, 1.0]`이다. 확률 자체가 덜 치우쳐 있으니 밀어줄 양도 적다.

**soft + bias가 Set A 서비스 prior에서 가장 좋은 조합이다:**

| (TEST, 서비스 prior) | 원본 7c | step3+bias | **soft+bias** |
|---|---|---|---|
| anxious recall | 0.5187 | 0.6129 | 0.6442 |
| anxious precision | 0.5410 | 0.4935 | 0.5130 |
| accuracy | 0.8193 | 0.8194 | **0.8278** |
| macro F1 | 0.7690 | 0.7849 | **0.7960** |
| neutral→anxious | 0.0765 | 0.1221 | **0.1191** |

anxious recall이 step3+bias보다 **높으면서** 오탐은 더 낮다. 정직하게 말하면 개별 지표 변화는 크지 않다(대부분 0.01~0.03). **soft의 값은 지표보다 보정에 있다.**

## 6. 4d — 백엔드에 제안: K-of-N

현재 규칙은 "anxious 확률 ≥ 0.5가 5초 지속"이다. **최근 N프레임 중 K프레임**으로 바꿀 것을 제안한다. 3fps에서 N = 15.

**2026-09-07 갱신: `deliverable/`의 현재 후보가 seed1+bias로 바뀌어(§5.1) p_fp·p_tp도 그 값으로 다시 계산했다.** bias `[0,1.4,0,1.9]` (p_fp = neutral→anxious = 0.0765, p_tp = anxious recall = 0.6173) 기준:

| K | 오탐 (파인튜닝, p=0.168) | 검출 (p=0.753) | 오탐 (+바이어스, p=0.077) | 검출 (p=0.617) |
|---|---|---|---|---|
| 6 | 0.0281 | 0.9993 | 0.0005 | 0.9755 |
| **7** | 0.0068 | 0.9962 | **0.0001** | **0.9268** |
| 8 | 0.0013 | 0.9841 | 0.0000 | 0.8257 |
| 9 | 0.0002 | 0.9470 | 0.0000 | 0.6626 |
| 10 | 0.0000 | 0.8589 | 0.0000 | 0.4580 |
| 12 | 0.0000 | 0.4735 | 0.0000 | 0.1146 |

전체 K=6..14는 `deliverable/bias_sweep.json`의 `kofn`. (참고: step3 기준으로는 K=7에서 오탐 0.0002/검출 0.9141이었다 — seed1이 두 지표 모두 더 낫다.)

### 결정 (2026-09-07): K = 7

바이어스를 적용하면 K=6에서 이미 오탐 0.0005로 매우 낮다 — 문제는 아래에서 지적하듯 이 숫자가 **독립 가정 하의 하한**이라는 것이다. 한 사람이 표정을 유지하면 프레임 오류가 상관되므로 실제 오탐률은 이 표보다 높을 수 있다. **K=7을 골랐다** — K=6 대비 오탐 상한을 5배 더 낮춰(0.0005 → 0.0001) 그 상관관계발 인플레이션에 대한 여유를 두면서도, 검출은 92.7%로 K=8부터 시작되는 급격한 하락(83%→66%→46%) 전에 머문다. K=6과 K=7의 검출 차이(97.6% vs 92.7%)는 4.9%p지만, 오탐 여유는 5배 넘게 벌어 — 서비스 신뢰도(불필요한 긴장 알림이 반복되면 코칭 도구에 대한 신뢰가 깎인다) 쪽에 더 무게를 둔 판단이다. Set B 데이터로 실제 상관관계를 측정하면 재검토한다.

**이 표는 정직하게 낙관적이다.** 이항 분포는 프레임 오류가 독립이라고 가정하지만 실제로는 아니다. 어떤 사람이 특정 표정을 유지하는데 모델이 그걸 계속 오독하면 오류는 상관된다. **K-of-N은 산발적 오탐은 잘 막고 체계적 오독은 거의 못 막는다.** 오탐 열은 상한이 아니라 하한으로 읽어야 한다.

그래도 비용이 거의 없다(백엔드 조건문 한 줄, 모델 변경 없음).

## 7. Set B — 여전히 비어 있음

스펙 §6.1의 채택 기준이고, Step 4의 어떤 것도 이걸 대체하지 않는다.

**A′(종횡비 보존)는 지금 있는 것 중 가장 강한 대리 지표다** — 검출기 열화까지 포함하므로. 하지만 그 아래 픽셀은 여전히 AI-Hub 스마트폰 셀피다. 노트북 센서, 사무실 조명, 학습 분포 밖의 얼굴은 답하지 못한다.

**녹화 도구를 만들어 뒀다** — [`scripts/setb.py`](../scripts/setb.py):

```
uv run python scripts/setb.py record --person <이름> --seconds 30
uv run python scripts/setb.py eval
```

4감정 × 30초 × 3fps ≈ 360프레임. 프레임은 **원본 센서 해상도로 저장**한다 — 3.4절에서 FE 변환 선택이 정확도를 0.35 이상 움직인다는 걸 확인했으므로, 변환은 녹화에 구워 넣지 말고 나중에 바꿔 가며 적용할 수 있어야 한다. `eval`은 스트레치·종횡비 보존 두 경로 모두로 평가한다.

**이건 사람이 직접 실행해야 한다** (웹캠 앞에서 표정을 지어야 하므로). n=1은 통계적으로 약하고 성능표에 반드시 `n=1`로 표기해야 한다. **한 사람은 무너짐을 보여줄 수는 있어도 충분함을 보여줄 수는 없다.** 그래도 0명보다는 낫다.
